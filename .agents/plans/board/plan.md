## 2. 本次范围

### 2.1 目标

1. 建立可构建、可测试的 TypeScript 单页前端工程。
2. 实现 Board 主界面，展示服务端列表、总数、加载、空状态和错误恢复。
3. 实现 Board 创建、详情、重命名和删除确认交互。
4. 实现五个 Board 接口的类型、运行时响应校验、错误归一化与结果未知处理。
5. 落实研究工作台视觉语言、响应式布局、键盘操作与基础可访问性。
6. 通过单元、组件和 Chrome 端到端测试验证关键流程与失败分支。

### 2.2 非目标

- 不实现文件上传、Item、目录、分类、知识、产物或 Agent 任务界面。
- 不实现登录、鉴权、用户切换或权限界面。
- 不实现搜索、分页、客户端排序、批量操作、软删除、回收站或恢复。
- 不修改后端项目、后端 Spec、后端 Plan 或后端实现。
- 不把本地缓存作为服务端 Board 数据来源，不引入离线写入能力。

## 4. 页面与交互设计

### 4.1 应用路由

- `/` 重定向到 `/boards`。
- `/boards` 展示 Board 主界面。
- `/boards/:boardId` 展示 Board 详情；直接刷新仍按路由参数重新请求服务端。
- 未知前端路径展示轻量 404 页面并提供返回 Board 主界面的入口。

### 4.2 Board 主界面

- 应用壳负责产品标识、内容宽度、背景和全局反馈区域。
- 页面头部负责标题、说明和主要创建按钮。
- 列表区域负责总数、刷新状态、卡片网格、加载骨架、空状态和加载错误。
- Board 卡片只展示服务端已确认的名称和 ID，并以明确链接进入详情。
- 创建使用模态表单；成功后展示已确认的新 Board，并重新读取列表以取得服务端顺序和总数。
- 创建已成功但列表刷新失败时，保留成功提示与新 Board 详情入口，同时把列表标记为可能过期，不伪造服务端总数。

### 4.3 Board 详情

- 首次进入按 `boardId` 请求详情；加载失败与 404 使用不同状态。
- 成功页以名称为标题，以定义列表展示 Board ID、创建人 ID 和根目录 ID。
- 重命名使用与创建一致的模态表单；成功后更新当前已确认详情，并重新读取详情。
- 删除位于独立危险区；确认对话框展示 Board 名称、不可恢复说明和非空 Board 保护。
- 删除收到 204 后返回主界面；若主界面列表刷新失败，显示删除已确认但列表可能过期的提示。

### 4.4 状态与并发

- 查询状态与每个变更状态分别管理，避免一个操作的错误覆盖另一个操作。
- 同一创建、重命名或删除请求提交期间禁用对应提交入口；页面其他只读内容保持可见。
- 不做乐观写入；只有契约校验通过的成功响应才更新已确认数据。
- 变更请求出现浏览器网络异常、超时或连接中断时进入 `result_unknown`，不自动重试，并提供“重新查询状态”的下一步。
- GET 失败由用户手动重试；切换路由时取消已经不再需要的查询，避免旧响应覆盖新页面。

## 5. API 与数据边界

### 5.1 运行时配置

- 应用启动时读取运行时注入的 `API_BASE_URL`；未配置时使用当前页面同源地址。
- 配置只负责基础地址，不包含业务路径、用户身份或凭据。
- 非法配置在应用启动区域显示明确错误，不静默拼接到未知地址。

### 5.2 Board API 客户端

- 在 Board 功能模块内集中定义 `BoardResponse`、`BoardListResponse`、请求体和 `ErrorResponse`。
- API 客户端封装五个端点、JSON 头、状态码判断、空 204 响应和响应体解析。
- 成功状态但响应字段缺失或类型错误时抛出契约错误，界面不得使用该数据。
- 错误归一化为业务错误、契约错误、网络错误和结果未知；用户消息与诊断信息分离，不展示内部响应正文。
- 变更 API 不包含自动重试器；查询 API 也不做无期限自动重试。

### 5.3 名称校验

- 创建和重命名共用一个名称校验函数：trim 后 1 至 200 个 Unicode 字符。
- 校验只负责空值与长度，不检查重名。
- 请求体只发送 trim 后的 `board_name`，不发送 ID、创建人、根目录或额外字段。

## 6. 自主设计项

1. **【自主设计】使用 Vite + React + TypeScript 建立 SPA。** 理由：当前工程为空，Vite 提供最小构建骨架，React 适合列表、详情、模态表单和异步状态的组件化组织；业务与框架适配层分离，未来可替换。
2. **【自主设计】使用 npm 和项目内锁文件。** 理由：Node 前端通用且无需额外包管理器前置条件；锁文件保证可重复安装。
3. **【自主设计】使用 React Router 管理 `/boards` 与 `/boards/:boardId`。** 理由：支持详情深链、刷新和浏览器返回；部署时需配置 SPA fallback，可替换为其他路由实现。
4. **【自主设计】使用原生 `fetch` 与 `AbortController`，不引入 Axios 或查询缓存库。** 理由：五个端点规模较小，原生能力足够；减少依赖并使禁止自动重试更易审计。
5. **【自主设计】用小型 TypeScript 类型守卫做运行时响应校验。** 理由：当前契约简单，避免引入通用 schema 库；校验函数集中在 API 边界，未来可换成 schema 工具。
6. **【自主设计】通过页面加载前的 `window.__UNDERREVISION_CONFIG__` 注入 `API_BASE_URL`。** 理由：满足运行时配置而不是仅构建时环境变量；默认配置脚本使用同源地址，部署时可替换。
7. **【自主设计】使用 CSS Modules 和全局设计 token。** 理由：颜色、间距、排版保持一致，同时把页面样式限制在组件范围；不引入 UI 组件库，避免视觉和依赖过重。
8. **【自主设计】创建与重命名复用一个可访问表单对话框，删除使用独立危险确认对话框。** 理由：复用相同输入语义，同时隔离不可恢复操作，降低误触风险。
9. **【自主设计】业务数据使用页面级 hooks 管理，不引入全局状态库。** 理由：当前只有 Board 单一功能域，路由和局部状态足够；API 与领域类型不绑定状态实现。
10. **【自主设计】测试采用 Vitest、Testing Library、MSW 和 Playwright Chromium。** 理由：分别覆盖纯函数、组件交互、HTTP 合同和 Chrome 关键流程；测试 mock 只用于开发与测试，不作为生产回退。
11. **【自主设计】视觉采用暖白背景、深墨色正文、低饱和蓝绿色强调色和砖红危险色。** 理由：形成克制的研究工作台气质并保持状态辨识；颜色集中为 token，可在不改交互契约的情况下调整。

## 7. 模块边界

- `app`：应用入口、路由、运行时配置加载和全局错误边界。
- `features/boards/api`：HTTP 请求、类型守卫、错误归一化和 Board API 类型。
- `features/boards/model`：名称校验、查询/变更状态和页面 hooks。
- `features/boards/components`：Board 卡片、表单对话框、删除确认、状态反馈和元数据展示。
- `pages`：Board 列表页、详情页和前端 404 页，只编排功能组件。
- `styles`：全局 token、基础排版和应用壳样式。
- `test`：MSW handler、测试 server、固定数据和端到端环境。

业务模块不得把服务端字段改名后冒充接口模型。组件只通过 Board API 与 hooks 访问远端数据，不在多个页面重复实现请求与错误解析。类、函数和 hooks 按职责拆分；复杂状态分支和结果未知逻辑使用便于审核的中文注释。

## 10. 风险、破坏性变化与回退

- **后端依赖风险**：后端 Plan 仍待审核，接口未必已实现。前端以自身 Spec 为硬边界开发；若后端契约变化，必须先更新前端 Spec、重新同步 Plan 并重新批准。
- **删除风险**：删除不可恢复。界面必须显式确认，且只以 204 判定成功；无法通过前端回退恢复已删除数据。
- **结果未知风险**：浏览器无法可靠判断网络异常时服务端是否已完成变更。界面保持未知状态并先查询核对，禁止自动重发。
- **SPA 部署风险**：详情深链需要托管服务回退到 `index.html`；部署配置缺失会导致刷新 404。
- **跨域风险**：非同源部署需要后端允许前端来源；前端不得通过放宽浏览器安全策略规避。
- **工程迁移风险**：旧 Python 空骨架当前已由工程师置于删除状态；实现只建立前端文件，不恢复或修改该旧骨架。
- **回退**：前端新增工程和页面可按提交整体回退；回退不会修改服务端数据。若已调用删除接口，代码回退不能恢复数据。
