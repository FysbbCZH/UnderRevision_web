# Board 管理前端设计

## 目标

- 为用户提供浏览、创建、查看、重命名和删除 Board 的浏览器界面。
- 前端行为与后端 Board 增删改查接口及领域模型保持一致，不在前端虚构后端尚未提供的能力。
- 所有请求都提供明确的进行中、成功、失败或结果未知反馈，不让用户面对无状态的等待。

## 配置项

- `{API_BASE_URL}`：前端运行时注入的后端服务基础地址；默认使用当前页面同源地址。跨域部署时，后端必须同时允许该前端来源。

## 详细设计

### 功能范围

本阶段提供以下 Board 管理操作：

1. 在主界面读取并展示当前 MVP 用户创建的全部 Board。
2. 创建 Board。
3. 查看单个 Board 的基本信息。
4. 修改 Board 名称。
5. 删除空 Board。

Board 增删改查是同步元数据操作，不展示为异步任务。每项操作仍必须展示请求状态与错误；请求超时或连接中断时，不得把未知结果显示为成功或失败。

### 页面结构

#### Board 主界面

主界面应包含：

- 页面标题和“创建 Board”入口。
- Board 总数。
- Board 列表；每项至少展示 Board 名称，并提供查看入口。
- 首次加载、刷新中、空列表和加载失败状态。
- 加载失败后的手动重试入口。

列表顺序完全采用服务端返回顺序，前端不自行重新排序。列表为空时应说明尚未创建 Board，并提供创建入口，不把空列表显示为错误。

#### Board 创建界面

创建界面可以使用独立区域、对话框或抽屉，但必须包含：

- Board 名称输入框及可识别标签。
- 创建、取消操作。
- 创建进行中状态。
- 输入错误或请求失败后的可读错误信息。

创建成功后关闭创建界面，在主界面展示新 Board，并允许用户进入其详情。创建失败后保留用户已输入的名称，方便修改或再次提交。

#### Board 详情界面

详情界面应包含：

- 返回 Board 主界面的入口。
- Board 名称、Board ID 和创建人 ID。
- 重命名入口。
- 独立的危险操作区及删除入口。
- 详情首次加载、加载失败和 Board 不存在状态。

Board ID 和创建人 ID 仅供识别与诊断，不得作为可编辑字段。Board 不存在时，应提示记录可能已删除，并允许返回主界面刷新列表。

#### Board 重命名界面

重命名界面应显示当前名称，并包含新名称输入框、保存和取消操作。保存进行中不得重复提交。只有收到后端成功响应后，详情和主界面中的名称才能更新；失败时保留输入值和原名称。

#### Board 删除确认

删除是不可恢复操作，必须在独立确认界面中展示目标 Board 名称并说明：

- 删除成功后无法恢复。
- 当前仅允许删除除唯一根目录外不含其他目录或业务内容的空 Board。
- 非空 Board 不会被部分删除。

用户必须显式确认后才发送删除请求。删除成功后返回主界面并移除该 Board；删除失败时保留当前详情，不得提前从列表或页面状态中移除。

### 视觉与布局

#### 整体风格

- 界面采用克制、清晰的研究工作台风格，以浅色纸张质感背景、深色正文和单一强调色建立层级，避免高饱和渐变、装饰性动画或过度拟物化。
- 页面信息密度应适合长期工作的桌面场景；标题、说明、元数据和危险操作必须具有清晰层级。
- 相同语义的状态、按钮和反馈在主界面、详情及对话框中使用一致的视觉规则。

#### 主界面布局

- 顶部区域展示产品名称、Board 页面标题、简短说明和主要“创建 Board”按钮。
- Board 总数与刷新状态位于列表标题附近，不与主要操作争夺视觉焦点。
- 宽屏使用卡片网格展示 Board，窄屏改为单列；卡片宽度应保证较长名称和标识信息仍可读。
- 每张卡片以 Board 名称作为主信息，Board ID 作为弱化元数据；整张卡片或明确按钮可进入详情。
- 空状态、加载骨架和加载错误应占据列表内容区域，避免页面结构在状态切换时明显跳动。

#### 详情布局

- 详情顶部以 Board 名称为主标题，返回入口和重命名操作保持清晰但不喧宾夺主。
- Board ID 和创建人 ID 使用定义列表或等价的成组布局展示，长标识允许换行或安全复制，但不得截断到无法辨认。
- 删除入口只出现在与常规信息区分开的危险操作区，不与返回、刷新或重命名按钮相邻放置。

#### 对话框与反馈

- 创建和重命名使用一致的表单容器、标签、错误位置和操作顺序。
- 删除确认使用明确的危险标题、目标名称和不可恢复说明；确认按钮采用危险语义样式，取消操作保持更易到达。
- 成功反馈应短暂且不遮挡后续操作；失败与结果未知反馈必须持续到用户关闭、修改输入或主动核对。
- 进行中状态可以使用加载指示，但必须同时提供文本，不得只显示无含义的动画。

### 页面状态

前端至少应区分以下可观察状态：

```typescript
type QueryStatus = "idle" | "loading" | "success" | "failure";

type MutationStatus =
  | "idle"
  | "submitting"
  | "success"
  | "failure"
  | "result_unknown";
```

- `loading` 和 `submitting` 状态必须提供可见的忙碌反馈。
- 同一变更处于 `submitting` 时，必须阻止重复提交。
- 已确认成功的数据不得因后续请求失败而从界面中静默消失。
- 请求已发送但因断网、超时、页面卸载或连接中断而无法确认结果时，使用 `result_unknown`。
- 变更结果未知时不得自动重试。用户应先刷新列表或详情核对服务端最终状态，再决定是否重新操作。
- GET 请求失败可以由用户手动重试；前端不得无期限自动轮询。

### 输入规则

- Board 名称提交前去除首尾空白。
- 名称长度必须为 1 至 200 个 Unicode 字符；不满足时不得发送请求，并在输入框附近提示。
- Board 名称允许重复，前端不得因列表中存在同名 Board 而阻止创建或重命名。
- `board_id` 必须来自后端已经确认的响应或当前路由上下文，不提供手工输入入口。
- 前端不发送或修改 `creator_id` 及其他未声明字段。

### 接口数据契约

#### Board 响应

```typescript
interface BoardResponse {
  board_id: string;
  board_name: string;
  creator_id: string;
}

interface BoardListResponse {
  items: BoardResponse[];
  total: number;
}
```

Board 根目录是后端内部容器，不属于 Board 响应，也不得在前端展示；目录操作遵循同层 `spec.directory.md`。

#### 请求体

```typescript
interface CreateBoardRequest {
  board_name: string;
}

interface UpdateBoardRequest {
  board_name: string;
}
```

#### 错误响应

```typescript
interface ErrorResponse {
  error: {
    code: string;
    message: string;
  };
}
```

前端优先展示后端返回的可读 `message`。响应不满足该结构、连接失败或响应无法解析时，展示统一的通用错误信息，不向用户显示堆栈、原始 HTML、SQL、本机路径或其他内部信息。

### 接口交互

#### 查询全部 Board

- 向 `{API_BASE_URL}/api/v1/boards` 发送 `GET` 请求。
- 只有收到 `200 OK` 且响应满足 `BoardListResponse` 时，才更新主界面列表和总数。
- `items` 为空且 `total` 为 `0` 时进入空列表状态。

#### 创建 Board

- 向 `{API_BASE_URL}/api/v1/boards` 发送 `POST` 请求，请求体为 `CreateBoardRequest`。
- 只有收到 `201 Created` 且响应满足 `BoardResponse` 时，才显示创建成功并把 Board 加入当前界面。
- `422 Unprocessable Entity` 时提示名称不合法并保留输入。

#### 查询单个 Board

- 向 `{API_BASE_URL}/api/v1/boards/{board_id}` 发送 `GET` 请求。
- 只有收到 `200 OK` 且响应满足 `BoardResponse` 时，才展示详情。
- `404 Not Found` 时展示 Board 不存在状态，不保留过期详情冒充有效数据。

#### 修改 Board 名称

- 向 `{API_BASE_URL}/api/v1/boards/{board_id}` 发送 `PATCH` 请求，请求体为 `UpdateBoardRequest`。
- 只有收到 `200 OK` 且响应满足 `BoardResponse` 时，才更新已展示名称。
- `404 Not Found` 时提示 Board 已不可用并引导用户返回主界面刷新；`422 Unprocessable Entity` 时保留输入供用户修改。

#### 删除 Board

- 向 `{API_BASE_URL}/api/v1/boards/{board_id}` 发送 `DELETE` 请求。
- 只有收到 `204 No Content` 时，才把 Board 标记为已删除并从当前界面移除。
- `404 Not Found` 时提示 Board 已不存在，并允许返回主界面刷新。
- `409 Conflict` 或错误码 `BOARD_NOT_EMPTY` 时明确提示当前 Board 非空，不能删除；不得尝试级联清理或隐藏失败。

### 一致性与恢复行为

- 创建、重命名和删除均不得自动重试；所有再次提交必须由用户明确触发。
- 不使用乐观更新冒充服务端成功。列表、详情和表单状态只在收到符合契约的成功响应后变更。
- 创建或重命名成功后，如果随后刷新列表失败，应保留已确认的成功结果并提示列表可能不是最新状态。
- 删除成功后，如果随后刷新列表失败，仍保持该 Board 已删除的本地确认结果，并提示列表刷新失败。
- 响应状态码成功但数据结构不符合契约时，视为前后端契约错误，不把响应用于更新界面。
- 前端不依靠 Board 名称识别记录；所有查看和变更均以 `board_id` 定位。

### 用户身份

本阶段不显示登录、注册、用户切换或权限入口。前端不发送用户字段；后端统一使用 MVP 用户 `dev_user/dev123456`，响应中的 `creator_id` 只作为结果数据展示。

### 可用性与浏览器行为

- Chrome 必须能够完成 Board 全部增删改查流程；Safari、Firefox 为可选支持。
- 所有表单控件和操作按钮必须具有可识别名称；状态、危险操作和错误不得只通过颜色表达。
- 对话框或抽屉必须支持清晰的关闭与焦点返回行为，删除确认不得被普通 Enter 误触发。
- 页面在常见桌面宽度下应完整显示；较窄窗口下不得出现阻止核心操作的横向溢出。
- 用户提供的 Board 名称和后端错误消息均作为文本展示，不得作为 HTML 注入页面。

## 约束

### 前后端契约一致性

- Board 基础信息模块只能调用本 Spec 定义的五个 Board 接口，不得假定存在搜索、分页、排序参数、批量操作、软删除、回收站或恢复接口；目录模块只调用同层 `spec.directory.md` 定义的接口；Item 模块只调用 `item/spec.md` 定义的接口。
- 前端发送和接收的字段名、状态码及错误结构必须与后端契约一致，不得在前端重命名后冒充服务端字段。
- 不得把尚未收到契约规定成功响应的创建、重命名或删除结果作为成功数据使用。
- 服务端是否允许删除以实际响应为准；前端不得根据当前页面数据自行断言 Board 一定为空。

### 数据一致性

- 变更请求不得并发重复提交或自动重试。
- 浏览器无法确认请求结果时必须明确标识结果未知，并通过重新查询核对，不得通过猜测更新成功状态。
- 列表总数采用服务端 `total`；前端局部变更后可以展示已确认结果，但不得伪造新的服务端总数。

### 范围限制

- 不实现账号、登录、鉴权和权限界面。
- Item 与本地文件管理遵循 `item/spec.md`；Board 基础信息模块不直接承担 Item、文件或分类交互。
- 不实现知识、产物、Agent 任务或异步任务管理界面。
- 不实现 Board 搜索、分页、排序设置、批量删除、软删除、回收站或恢复。
- 不把 Board 数据持久化到浏览器缓存以替代服务端查询。
- 不选择或强制规定具体 TypeScript UI 框架；框架选型应在后续 Plan 中完成，但不得改变本 Spec 的行为和接口契约。
